# CH-06B2b 接续准备：由选定的历史片段辅助一次回答

2026-10-20，依据当前 B2a 工作树及已有模型许可、原生确认、调用账本源码整理。本文件是下一片的设计准备，尚未实现，也不表示获准外发真实资料。B2a 的交付与复核以其独立记录为准。

## 最小范围

律师明确选择当前对话、当前案件绑定下的 1—8 条已保存片段，保留现有问题草稿，在原生窗口核对完整待发送内容后，执行一次主模型回答。来源检索运行保持终结；回答创建新的消息和运行，关联原有引用。不得重新打开已经完成的检索运行，也不得借用其 request_id。

复用现有主模型任务、排队、费用预留、一次 claim、取消和恢复机制。首片不接多轮工具调用、自动追加检索结果、附件正文或 Jev 辅助；普通文字路径及其既有许可格式保持兼容。随后 B2c 再处理最多 4 轮模型调用的独立账本约束。

## 需要同时闭合的接口

| 接口 | 最小职责与实际复用位置 |
| --- | --- |
| 选定来源 | 页面只提交有序且不重复的 saved_citation_id，以及草稿和范围版本；由 `assistant/library_handlers.py` 的 `read_saved_citation` 从服务器重建片段、版本、位置、摘要和权限。不能信任页面传来的标题、正文或核验状态。 |
| 本机预览 | 服务器确定性地重建问题和选定片段；不查询当前法库、不创建运行、不授予许可。原生进程自行读取预览，并在确认前后比较完整摘要、选择顺序、会话和配置身份。 |
| 内容许可 | 新的明确格式绑定完整问题、选定片段、模板版本、接收方、费用预算和一次调用；不能把资料摘要塞入旧 `MainSendApproval.content_sha256` 冒充普通文字。复用 registry 的撤销、配置版本和 nonce。 |
| 持久登记 | `providers/attempts.py` 既有短事务同时冻结输入、内容清单、配置、许可和一次 attempt；同请求重放读回，内容变化冲突。`task_manager.py` 共用容量与退出清理，不新建队列。 |
| 执行与结果 | 沿用现有传输限制、超时、无自动重试和费用回执。主模型只能引用本次许可中的已保存 UUID；返回其他引用、伪造核验状态或替换原文时拒绝采用，已发生费用仍如实记账。 |
| 恢复 | 归档检查内容清单、引用身份、来源关联、许可与输入摘要；当前法库离线和历史会话撤销不妨碍合法快照保存。恢复仍撤销会话、隔离运行，不能重新授权或重发。 |

## 数据与许可边界

- 第一片只接受同一所有者、工作区、对话、当前 binding_revision 和案件范围的已保存片段。来源的 input_revision 可以较旧；能访问两个案件并不自动允许把它们混入同一回答。
- 明确列出真正外发的字段：标题、有界原文片段、必要的位置与版本标识、已保存引用 UUID，以及原问题。原始文件路径和无关元数据默认不外发；完整 `CitationRef` 继续保留本机。支持性、适用性和人工审核状态仍按原记录显示。
- 预览须完整覆盖实际外发的文字和字段，包括可展开核对的系统模板；规范 UTF-8 字节分别生成内容清单摘要和最终传输摘要。8×1,200 字的引用上限不保证符合配置的总输入预算，预览与 claim 均需检查完整请求大小。
- 不能形成“摘要包含自身”的循环。若实际传输加入新消息 ID，须明确区分已批准内容清单与服务器最终封套，并检查只增加允许的服务器字段；不能确认后偷偷增加内容。
- 点选、撤选或改变问题会使旧确认失效；关闭或重启后重新确认。不因当前法库变化自动刷新已选片段，刷新得到的是另一次显式选择和许可。
- `save_message` 会推进 input_revision 和 composer_revision。claim/settlement 必须核对登记后的确定后继状态，不能拿登记前版本直接比较，也不能接受任意最新版本。
- 这项后继 composer/选片检查是上下文路径要新增的约束，当前 `attempts._current` 并未完整提供。来源撤权后仍沿用 settlement 的真实费用记账及提交后再次检查 fence/claim 的顺序，不因答案不可采用而丢弃费用。
- 未知发送结果通过已有运行/历史只读入口找回，不自动重新授权、重放 POST 或派发。当前旧请求登记仍先检查 runtime/许可，不能把“同请求不重复执行”表述为重启后无需许可即可重放所有 POST。
- 本机预览可以先保持临时状态；最终批准输入在既有登记事务中不可变保存。恢复尚未提交的选片草稿是另一项需求，不能顺手增加第二套持久草稿系统。

## 版本与拆分决策

所有业务 DTO 仍只在 `domain.py`。增加明确的上下文 codec 和许可类型，旧 V1 的规范 JSON、哈希和历史字节不可因增加默认字段而改变。`providers/main.py` 复用已有传输，按明确输入类型选择请求与结果编解码；不复制第二套供应商客户端。

完整分派还要覆盖 registry 的 grant/lease/provider 包装，policy.prepare，attempts 的读取、登记、claim、settle，以及 history 与归档校验。每条 attempt 必须有不可变的格式身份；不能靠“查到清单就是 V2，清单缺失就按 V1”降级放行。上下文的 run/attempt/清单/来源原子登记，缺行、孤立关系或格式矛盾一律拒绝。

上下文入口在 manager 明确跳过 `_reserve_judge` 和后续辅助执行，不能只隐藏原生窗口勾选框；即使当前会话存在合法 Jev 许可，也必须产生零辅助调用。共用的是容量、生命周期和传输，不是无条件复用普通文字的每个阶段。普通模型历史现有 binding_revision 限制不在本片放宽。

现有 attempt/output 的 UNIQUE(run_id) 足以支持本片的一次回答，但不足以支持 B2c 多轮。含引用的新输入不能只因为“SQLite 能保存 JSON”就绕过版本识别：`model_integrity.py` 和 `storage_schema.py` 会核对严格格式与已知结构。实施前应在小范围存储审查中确定以下一种明确方案：

1. 新 schema 版本增加与既有 attempt 关联的不可变上下文清单/来源关联，继续共用原任务账本；优先考虑此方案，使旧应用能明确拒绝不支持的数据。
2. 若已有独立的数据格式版本屏障能够可靠阻止旧应用读取，则可采用严格 V2 输入封套；必须证明旧格式不变、旧程序拒绝和备份分派可靠，不能用可选字段静默扩大 V1。

这不是增加一套工作流平台。具体表结构尚未确定；需把 schema、升级、备份创建、恢复、旧版拒绝和来源依赖放在同一切片，不先发一个“能调用”的半成品。

## 首批合成验收

- 旧文字许可不能发送含资料请求；伪造、跨案、重复或未获权引用均拒绝。
- 原生预览和真实传输字段、字节预算一致；改变问题、选片、账号、配置、权限或恢复状态均不能沿用旧许可。
- 同 request_id 不二次派发；未知结果不自动重试；取消或撤权后实际使用量保留、迟到答案不采用。
- 引用中的恶意提示仅作资料，结果引用必须属于批准集合，不能把模型的“已核验”当事实。
- 禁止模型控制结构化核验状态、原文和引用身份；这不表示能够自动识别任意自然语言中的错误法律结论。即使已有有效 Jev grant，上下文路径仍须验证辅助预留与请求均为零。
- 当前法库离线或变更不改写历史片段；归档创建和恢复均拒绝损坏的内容清单或来源关系。
- 普通文字 V1、原生确认、旧模型账本和恢复回归保持通过。真实供应商、账户与费用验证另记实际前提。
