## 1. 产品目标与非目标

### 1.1 产品目标

建设为：**一个对话入口 + 四项核心业务能力 + 一个任务中心 +
一套客户/案件/材料体系 + 统一模型服务接口。**

律师只需在一个聊天界面输入自然语言、上传文件或点击技能卡片。系统负责识别意图、关联客户与案件、整理材料、调用业务能力、记录执行状态、生成成果并保存到统一档案。

四项核心能力：

1.  **客户接待：**
    识别诉求、程序阶段、关键事实、证据、紧急事项和待追问问题；生成内部接待底稿与客户回复草稿。
2.  **案件整理：**
    整理事实、证据、时间线、争点、请求权基础、证据缺口和文书草稿。
3.  **合同审查：**
    读取合同及附件，逐条识别风险，提供修改建议，保留条款定位和材料版本，复用现有审查成果链。
4.  **模拟法庭：**
    调用持衡已有对抗推演能力，组织己方律师、对方律师和法官视角的独立回合，保存回合、论点和依据。

### 1.2 非目标

-   不重写现有合同审查引擎、材料解析器、微信传输层或共享法库。
-   不把 DeepSeek Harness 整个复制进主仓库。
-   不建立第二套会话、任务、权限、材料或费用账本。
-   不把"菜单出现""Skill 已安装"当作功能接线完成。
-   不开发客户微信托管、群聊监控或批量客户消息接管。
-   不做模型自主无限循环或无人监督办案。
-   不承诺全国完整法律数据库。
-   不以模型输出替代律师对事实、证据、法源、法律适用和成果签发的审核。

**S1：否定指令保护残余缺陷（P1）。**

`contract`，触发一次模拟模型调用，批次变为
`completed`。预期应保存来件、停止合同分析，主模型调用为
0。报告没有证明真实客户材料已经外发，不得夸大为已发生真实泄漏。

**S2：补件后继续处理路由回归（P2）。**
原事项已处理一次后，用户发送"继续整理材料"、上传附件、再发送"可以开始"。预期归入原事项并继续执行，模型调用数由
1 增至 2。实际第二批进入 `clarify`，未关联事项，模型调用数仍为
1。报告将其归因为续接判断过度依赖最后一行，且倒数第二行只接受少数完全匹配短语。

### 4.2 统一业务对象

先检查现有数据库和数据模型，优先扩展已有对象，不要平行新建。目标概念至少包括：

-   `Conversation`：聊天会话。
-   `Client`：客户档案。
-   `Case`：案件档案。
-   `Task`：一次可追踪的业务任务。
-   `TaskBatch`：一次消息/材料批次。
-   `Material`：原始材料。
-   `MaterialVersion`：材料版本及摘要。
-   `SkillInvocation`：技能调用记录。
-   `ModelRun`：模型运行记录。
-   `Artifact`：生成成果。
-   `Approval/Permission`：操作授权和范围。
-   `AuditEvent`：审计事件。

这些是目标语义，不要求机械新增同名表。必须先做现有表结构映射，能复用就不新建。

### 4.3 底层神经网络伙伴的接口边界

底层技术伙伴负责模型/神经网络能力、推理服务、性能优化和模型运行环境；群兴主项目负责法律业务流程、客户案件关系、权限、材料、任务、费用账本、成果和审计。

双方通过明确、版本化的服务接口协作。先盘点伙伴现有服务协议、输入输出、部署方式、模型清单、超时/错误语义、并发能力、数据保留和日志策略，不预设其技术栈或能力。

必须形成统一模型适配接口，至少规范：

-   `provider/model` 标识与能力声明；
-   输入消息、附件引用和上下文长度；
-   请求 ID、任务 ID、幂等键；
-   流式/非流式响应；
-   超时、取消、重试及未知结果；
-   Token、计费单位和费用估算/实耗；
-   模型版本、运行时间和错误码；
-   数据是否离开本机、保留期限和日志脱敏。

模型服务不能自行决定是否有权读取客户案件、启动新任务、解除暂停或发送微信。业务授权必须由群兴主应用控制。模型输出是建议和草稿，不是法律签发。

## 5. 统一任务、消息归集与权限规则

### 5.1 任务关联原则

桌面和本人微信通道必须共用同一任务关联服务。微信只是消息入口，不是独立业务系统。

必须支持：

-   先发附件、后发指令；
-   先发指令、分多次上传主合同及附件；
-   一次任务中多条文字和多个附件；
-   补件、材料更正、材料撤回；
-   用户明确暂停、取消或改为只接收材料；
-   多个事项并行时不串案；
-   重复消息、重复附件和回执丢失时不重复执行。

不得仅以"最后一条消息"判断整个批次意图。应依据完整批次事件、消息顺序、任务关联、当前状态及最新有效指令综合判断。

### 5.2 状态机最低要求

先核实现有状态枚举并复用，禁止另建冲突状态。至少能表达：

`collecting -> ready -> queued -> running -> completed`

并支持：

-   `waiting_for_material`
-   `clarify`
-   `paused`
-   `cancelled`
-   `failed`
-   `unknown`

每次状态变化必须记录触发事件、操作者/来源、时间、任务 ID
和原因。未知状态不能推定成功，也不能盲目重发。

### 5.3 取消与否定优先级

明确的暂停、取消、撤回、只接收材料指令，必须优先于自动策略和技能建议。

覆盖测试至少包括：

-   "暂时不审查""不再审查""先别分析""只接收材料""停止处理"；
-   先暂停后补充附件；
-   先启动后取消；
-   引用转述中的否定语句；
-   条件句中的否定；
-   用户明确重新开始；
-   多事项场景中仅取消指定事项。

歧义时进入等待澄清，不得擅自调用模型。保存材料与执行分析是两个不同动作；只接收材料不得触发业务分析。

### 5.4 材料、权限和费用保护

-   原始材料不可被新版本覆盖；更正应产生新版本并保留来源。
-   每次模型运行绑定确切材料版本、提示词/技能版本和模型版本。
-   任务只能访问当前用户授权的客户/案件范围。
-   撤权后不得继续读取或启动新运行。
-   每次运行记录费用/Token；未知费用明确标记未知。
-   重复请求使用幂等键；未知结果先查询状态/回执，不得自动重发。
-   客户可见稿与内部策略、律师工作底稿必须结构化分离。
-   自动执行仅限已授权范围；签发、发送、提交法院、和解、放弃权利等必须保留明确人工决定点。

## 6. 前端改造与 Nielsen 十大原则

### 6.1 交互目标

参考 DeepSeek Harness 的 Chat-first
体验，但保留群兴现有后端、权限和任务系统。推荐布局：

-   **左侧：** 新建对话、历史会话、客户和案件导航。
-   **中间：** 主聊天、附件上传、AI回答、成果预览。
-   **右侧：** 当前任务、材料列表及版本、调用技能、进度、成果；可折叠。
-   **输入区上方：**
    客户接待、案件整理、合同审查、模拟法庭四张技能卡片。
-   点击技能卡片只是在当前会话选择能力，不打开独立工作台。
-   自然语言输入也必须能自动识别并调用能力。

### 6.2 Nielsen 十大原则及可验收要求

  ---------------------------------------------------------------------------------------------------------------
  原则                    群兴工作台的实现                                     验收方式

### 6.3 前端验收要求

-   新建会话、历史会话、附件上传、拖放、回车发送、停止生成等基本操作不得退化。
-   上传附件时继续输入文字，不得误发或丢失草稿。
-   切换会话不得把迟到响应写入错误会话。
-   当前任务、材料版本、运行状态和成果引用必须可见。
-   页面不展示"已完成"除非后端任务状态确实完成。
-   不得只做静态视觉稿；必须连接真实业务 API 并通过浏览器/桌面合成测试。
-   先做现有前端组件盘点，优先复用现有组件与样式系统。

## 7. 分阶段实施计划

### 阶段 0：只读盘点与环境确认（阻断后续修改）

**任务：**

1.  检查
    `git status --short --branch`、`git log -1 --oneline`、`git diff`、`git diff --cached`、未跟踪文件。
2.  核对 `desktop/package.json`、Python/Node
    版本、锁文件、项目入口和开发脚本。
3.  读取 README、AGENTS/开发规范、任务状态、架构文档、0.6.0审计材料。
4.  找出桌面主入口、微信入口、任务路由、材料装配、提示词选择、模型调用、数据库、成果输出和前端入口。
5.  检查三个仓库本地 clone、分支、提交和工作区；固定实际要用的 commit。
6.  输出文件级架构图、调用链图、现有数据模型映射、测试命令清单和风险清单。

**完成条件：**
有可复查的源码定位和当前环境记录；所有用户未提交内容已识别并保护。未完成前不得重构。

### 阶段 1：修复 S1 与 S2

**S1：**
先建立自然语言否定、取消、只接收材料、引用转述、条件句和多事项反例。修复后明确暂停/取消优先级最高；歧义进入等待；只接收材料时模型调用数为
0。

**S2：**
将批次内的"事项续接指令"与"材料就绪指令"分开识别。保留完整事件序列，不以最后一行覆盖此前有效续接意图。必须覆盖旧事件迟到、取消后旧事件、补件和多事项歧义。

**回归：**
撤权、未知不重发、幂等、材料版本、费用账本、权限隔离和现有微信合成测试全部重跑。

**完成条件：** 审计报告中失败的反例全部转绿；相关保护测试仍通过；保存
RED/GREEN 日志及基线对照。

### 阶段 2：统一 Skill/项目适配层

1.  建立现有能力注册清单，包含名称、版本、输入/输出
    Schema、权限、数据来源和状态。
2.  先接入家事
    Skill，保留完整文件树、索引、来源和许可；通过适配器向统一任务服务注册。
3.  接入持衡模拟法庭和共享法库；固定来源
    commit，调用既有接口，不复制法库。
4.  将九份接待知识资料接入统一检索链，保留检索来源、文档名、片段位置、摘要/版本和权限。
5.  对每次调用记录
    `skill_id/version`、输入材料版本、检索片段来源、输出成果和执行状态。
6.  如果某 Skill
    缺文件、版本不兼容或法库不可用，显示明确降级状态，不静默回退成普通模型回答。

**完成条件：** 从统一聊天入口触发时，运行日志能证明真实调用对应
Skill/适配器，并能回溯读取了哪些资料；不能只看 UI 标签或配置文件。

### 阶段 3：统一模型服务接口与伙伴联调

1.  盘点底层伙伴已有神经网络/模型服务接口，形成接口协议，不假设技术栈。
2.  复用群兴当前模型调用账本和配置机制，建立适配层，不引入第二套模型会话系统。
3.  实现 Mock Provider，用于无密钥、无费用的完整验收。
4.  统一请求
    ID、幂等键、超时、取消、流式输出、未知结果、错误码、Token/费用记录。
5.  验证模型不可越权访问案件、不可解除暂停、不可自行创建授权。
6.  完成伙伴服务的隔离联调后，再由用户决定是否批准真实模型小规模测试。

**完成条件：** Mock
全链路通过；伙伴接口契约、数据边界、日志策略和失败处理有文档及测试。

### 阶段 4：Chat-first 前端改造

1.  盘点现有前端框架和组件，确定最小改造路径。
2.  实现左侧导航、中间聊天、可折叠右侧任务上下文。
3.  增加四项技能卡片，卡片与自然语言共用同一任务路由。
4.  统一展示任务状态、材料、版本、技能调用、模型运行、成果和错误恢复。
5.  桌面与微信展示同一任务状态，不另造业务状态。
6.  按 Nielsen 十大原则执行交互走查和可用性测试。

**完成条件：**
不改变现有核心业务能力；主流程可从聊天完成；关键操作有自动化 UI
测试及人工走查记录。

### 阶段 5：四项业务端到端验收

使用完全虚构、标记为 synthetic
的数据，不使用真实客户材料。每项能力均验证：输入、路由、材料、技能、模型、权限、费用、成果、回读和审计记录。

### 阶段 6：本人微信受控试点准备

本阶段先做合成环境验收，不扫码、不连接真实微信。用户另行批准后，才在其本人电脑执行真实账号试点。真实试点必须逐项人工确认，不扩展到客户账号或群聊。

## 11. 回滚与停止条件

### 11.1 回滚要求

-   修改前保存 Git 状态、工作树 diff 和未跟踪文件清单。
-   数据库变更必须有向前/向后迁移方案；禁止直接删除旧字段或旧数据。
-   Skill 和适配器按版本注册，可禁用回退，不删除原始来源。
-   前端改造保留可回退版本或独立分支。
-   不覆盖现有安装版和用户数据库。
-   回滚后验证旧任务、旧材料和旧成果仍可读取。

### 11.2 立即停止条件

出现以下任一情况，停止当前阶段并报告，不得自行绕过：

-   发现用户未提交修改可能被覆盖；
-   发现权限、撤权或客户/内部稿隔离失效；
-   暂停/取消仍可能触发模型调用；
-   未知请求会自动重复发送；
-   材料版本被覆盖或跨案件读取；
-   费用账本与实际调用不一致；
-   引入组件许可证不明或要求不兼容；
-   伙伴服务需要上传真实案件数据但没有明确授权；
-   真实微信/真实模型/生产数据库操作超出授权；
-   关键测试失败且无法解释，或测试环境与目标环境不一致。
