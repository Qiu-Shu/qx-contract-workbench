## A1/A2 目标结构

复用现有FastAPI、SQLAlchemy、案件服务和Fact确认。运行默认仍是mock_demo；assisted_draft通过可信服务端参数显式选择，须提供限定hash的独立虚构资料政策。客户端上传名称、自报身份、JSON instruction或真实供应商密钥不构成该政策。

候选分两步：事实候选绑定当前原件/锚点、只追加未确认事实；意见候选绑定已确认事实/文档/立场/规则/政策的完整上下文版本，保存不可变proposal及run。公共输入排除Actor和审批标识；执行收据由后端生成，人工/合成来源明确为无真实模型调用。不得在assisted中用“等于固定Mock答案”校验观点；仍核schema、范围、引用、版本、来源和预算，不将任意建议认证为法律真相。

意见含basis_kind、待核引用与unknowns；未核法源不能被标为已核，不把候选直接写入确认事实。未审维度显示未完成，任何结果都保持草案与来源限制。QCC关闭只显示未查询，材料内审查继续。

新增12份标准办公格式独立虚构合同，四首发类型各3份；至少同名不同主体、重复句及金额单位变化。它们与原四例hash不同，计划逐个跑入案→解析→候选→事实确认→新意见→律师改写/驳回→草案导出/版本失效。输入、期望及实际输出分别保留，透明人工/合成候选不称真实推理成绩。

### 首个接口切片的具体边界

通过服务端 `create_app` 的显式辅助政策登记模式、固定虚构文件 hash 和人工候选来源；不改变 `Settings` 默认值或 `require_provider` 的 mock 注册门。辅助模式解析只保存原文及空的未确认事实快照，之后由候选事实接口复用 `build_fact_candidates`、完整追加快照和现有律师确认流程。候选需携带当前文件 UUID/hash 与预期事实版本，客户端不能提交确认人或批准状态。

意见提交前，由服务端返回当前上下文 hash（案件立场/目标、所有当前文件、已确认事实、规则和政策及显式辅助政策）。意见输入绑定该 hash、事实版本和文件集合，引用必须属于当前可消费原文锚点；未核法源保持 pending。只在 `review/proposals.py` 核验候选，不新建案件或导出引擎。服务端分配 run/finding/proposal 身份并保存不可变关联记录，人工输入收据明确 real_model_calls=0、无供应商 token 或费用证明。

既有 ReviewRun、律师处置、补丁与草案导出继续复用。候选来源、待核依据和未知项进入可读输出；候选没有涉及的维度继续材料不足，不能按“成功保存”自动标已审无问题。当前运行校验要分辨受保护的辅助 proposal 与 mock attempts，不通过换 provider 字符串接收任意伪造 run。工作台新增有限的人工候选录入，默认演示界面保持原路径；不要求律师编辑 JSON。

12 个实际 API 旅程从新源文件上传开始，分别添加原文绑定的事实候选、确认事实、提交与 mock 不同的意见、改写/驳回、下载草案并核对实际 DOCX 句子及旧成果失效。原件/hash、每阶段版本、制品字节 hash、QCC/真实模型调用状态独立记录。API 旅程不替代浏览器视觉验收、法律 gold 或真实推理。

## 验证要求

先写缺功能/行为不符的失败测试并记录exit和断言，再实现目标功能；未知锚点、旧版本、跨案/撤销、超限、instruction数据化、来源待核、默认离线、QCC0和formal拒签均有反例。依赖切片完成后跑实际新旅程，独立审阅并记录完整回归。实际结果写阶段记录和TASK_STATUS，完成项与阻断项分别登记。
