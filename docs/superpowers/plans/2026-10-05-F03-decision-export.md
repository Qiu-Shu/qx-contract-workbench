# F03：律师处置与成果版本闭环

状态：原 v2.0 范围内的缺陷修复，实施中。用户随后于本轮明确确认 CR-01 律师辅助工作稿路线；本修复在原范围已获授权，新范围见 ADR 0006。开发基线 `4d0f65abd825f7335c41f72e2209282241be6867`；沿既有 `codex/contract-review-v2`，保留已有实现和历史证据。

## 授权与依据

原用户已授权 v2.0 增量实施，规格第1节要求接受、编辑、删除、补查、转专项；第10节要求结论等变化使旧批准失效，输出按受众过滤。F03 是既有处置接口写入历史而导出不消费、旧成果不失效的缺陷。附件整改书仅作技术参考，不能自动启用 assisted、真实模型、真实文件或签发。

本机独立虚构后端探针实际复现五种处置都未改变客户投影，五种变化后旧 bundle 均可下载；这些是局部探针，不是 HTTP 端到端或 pytest 通过记录。

## 最小设计

1. 在唯一领域模型文件增加明确的律师改文与不可变处置快照；原 ReviewRun、原意见、处置历史仍保留。最新处置用于有效视图。编辑理由不能代替改文，历史 reason-only 编辑明确为待完成编辑。
2. 接受保留当前有效意见；明确编辑输出律师改文；驳回不再成为客户建议；补查和转专项成为待办。内部保留原意见及处置历史，对方仅有已批准修改和解释，不泄漏内部底线。
3. bundle 绑定处置快照 hash；生成结束、读取、下载及批准时重新核验。处置变化使旧成果不再是当前成果；文件和不可变记录保留，本轮不新增公开历史下载接口。
4. 被驳回、补查、转专项意见对应的旧补丁不得继续对外生效；编辑改文与精确补丁须一致且有现有批准，不能把意见编辑当成改原件批准。
5. 保留对象权限、会话重核、审批者撤销、跨案、原件哈希、事务文件清理、mock 拒签。前端补上明确改文输入，服务端核验。
