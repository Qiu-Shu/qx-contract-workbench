# T02 持久化、案件权限、版本和追加审计

在已获准当前开发分支增量实现；依据v2.0 §1、5、T02。开发仅虚构数据，SQLite局部试运行，真实认证部署尚未批准。

1. 先建立四项明确失败测试：同hash跨案件仍403、admin非成员仍403、原版本不可修改、审计没有密钥/正文。补会话失效/角色伪造、外键和事务回滚测试。
2. SQLAlchemy 2 表及外键保存用户、会话、案件、membership、不可变文档版本和追加审计。业务snapshot由T01模型验证；UUID/UTC/Decimal存储不得丢类型。SQLite连接启用外键，原文存储使用案件/版本ID而不是全局hash缓存。
3. `authorize(actor, matter_id, action, db)`先从DB验证活跃会话/用户角色，再查membership及动作；admin没有案件读取特权。客户端Actor自报角色不能批准操作。批准签发仍由后续T09核对全部快照及双审。
4. `create_version(input, actor, db)`授权后登记版本；内容先由T03摄取写到服务控制位置，登记时从文件流计算hash/大小，不信任客户端自报hash。原件不可覆盖，supersedes必须在同案。文档解析结果另外保存，不能修改原件快照。
5. `append_event(event, db)`保存固定字段与hash；自由理由只保留受控代码/摘要，未知敏感正文和凭证字段不进入日志。DB层禁止审计及版本UPDATE/DELETE；不靠UI或Python对象frozen单独保证。
6. 本地密码采用维护库Argon2；会话ID及CSRF由服务生成，API依赖不接受客户端任意user_id/roles。使用FastAPI/Starlette接口，默认无账号、无真实数据、无对外服务启动。T10接入可操作UI。
7. 目标测试及T00/T01回归通过，独立权限/事务review，实际结果写`docs/testing/T02.md`和TASK_STATUS，再本地提交。未实现/部署/批准项保持明确状态。

接口决定：VersionInput仅规定上传元信息，缺少内容无法算真实hash。保留规格前三个位置参数，增加显式关键字`content: BinaryIO`供服务调用；未传内容明确失败，不生成假空版本。原件根由服务配置，不接受客户端任意路径；T03摄取负责魔数及资源校验，T02登记再执行授权、配额和不可变写入。记录该接口细化与限制，不另造重复DTO。

依赖：选择实际可下载的SQLAlchemy2、FastAPI、pwdlib[argon2]及其完整传递依赖；按Windows CPython3.12 wheel重算hash、保留许可、生产批准为空，更新应用lock。T01报告保留其当时11包分母，后续新增不能冒充此前已测。
