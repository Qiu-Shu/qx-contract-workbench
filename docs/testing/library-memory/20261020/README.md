## 本片变化

现有检索与对话法库适配器只需要一个命中的原文起止位置，原实现却为整篇文书建立逐字坐标表。两处现在复用 `library.text.original_span`，按既有逐字符规范化规则扫描到命中终点，只保存计数及两端位置。旧 `normalize(with_map=True)` 及索引构建契约保持；没有新依赖、schema、进程或主入口职责。

空白合并、零宽删除、Unicode兼容展开及组合字符仍保持原有Python字符坐标；查询、排序、片段边界、来源摘要/代际及权限核验逻辑未改。保存的引用含义仍是记录和原文相符，不证明法律支持性或适用性。

## 同材料前后测量

同一条250,009字符合成案例，目标词位于末尾；CSV摘要、索引代际及完整返回JSON摘要逐一相同。每条路径先暖缓存，再独立计时3次、另用tracemalloc测3次分配峰值，中位数如下。完整样本及三个产品文件摘要见[改动前](baseline.json)、[改动后](final.json)，构造方法见[脚本](measure.py)。

| 路径 | Python跟踪分配峰值 | 降幅 | 未开启跟踪的耗时 |
| --- | --- | --- | --- |
| 既有法库检索 | 27,134,250 → 3,330,636字节 | 87.725% | 81.49 → 88.14ms（+8.15%） |
| 对话法库适配 | 27,135,867 → 3,332,261字节 | 87.720% | 171.48 → 181.69ms（+5.95%） |

本片接受这个样本中约6.64/10.21ms的耗时增量，以移除整篇映射的额外分配。3次暖缓存测量不是统计显著的普遍性能结论；峰值不含追踪前的既有缓存全部占用，不是进程RSS、Electron占用、冷启动、可输入时间或安装包大小。多候选接近搜索截止的负载未测，不能声称整体更快或超时频率不变。

实际测量命令是 `.venv/Scripts/python.exe -X utf8 .local/library-memory-20261020/measure.py baseline` 及同脚本的 `final`，均exit0。复跑时将本目录脚本放入隔离的同名本地证据目录；baseline须使用上面的固定Git基线，不能用当前实现生成“旧版”数据。原合成CSV/索引保持本机，不进入Git。
