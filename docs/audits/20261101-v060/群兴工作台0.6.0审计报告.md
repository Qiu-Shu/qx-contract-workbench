## 4 Standards 工程规范和行为审查

以下为独立 Standards 审查的两项发现，顺序保留。P1 表示扩大自动处理前应优先修复；P2 表示会阻断正常业务续接。此处不是把代码风格意见当成生产缺陷。

### S1 P1 否定指令保护仍会漏掉常用表述

位置：`src/cn_contract/assistant/business.py:29`，微信入口使用该判断的位置为 `src/cn_contract/weixin_inbox/service_runtime.py:245`。

触发方式：在启用自动策略的合成环境中，分别发送“新事项：暂时不审查合同，只接收材料”及“新事项：不再审查合同，只接收材料”，附一份虚构合同。

预期保存来件、停止合同分析，主模型调用为 0。实际两次都识别为 `contract`，各触发 1 次模拟模型，批次成为 `completed`。原因是固定否定词正则包含“不要、暂不”等，却漏掉“暂时不、不再”；后续权限和费用许可无法补救已经错误识别的用户意图。

这违反规格 0.1 的最新指令优先与 0.6 的代码授权控制要求。独立基线比较表明 0.5.8 也存在该类缺陷，准确归类为**0.6.0 宣称修复范围内的残余缺陷**，并非本轮新增回归。风险是在实际启用模型时可能违背暂停意愿，把材料继续送入已配置的处理链；本次只用模拟模型证明触发路径，没有外发真实材料。

建议：先增加覆盖自然否定、条件句、引用转述及多消息取消的反例，再让歧义或明确暂停优先进入等待。仅追加两个词不足以证明中文意图判断已全面可靠。

### S2 P2 补件后的开始指令会覆盖继续处理意图

位置：`src/cn_contract/weixin_inbox/service_routing.py:55`。

触发方式：唯一事项已处理一次后，依次发送“继续整理材料”、附件、“可以开始”。预期继续同一事项，模型总调用数由 1 增为 2。实际第二批进入 `clarify`，没有归属事项，模型总调用数仍为 1。

原因是新逻辑只以最后一行判断继续意图，对倒数第二行仅接受三个完全匹配的短语，“继续整理材料”不在其中。固定基线同输入为 `start/existing/case`，当前为 `clarify/unassigned`，确认是本轮引入的续办回归。不会因此错误发送给其他事项，但会让清楚的补件指令停住。

建议：区分批次中的事项续接指令和材料就绪指令，保留有效续接意图；同时维持多事项歧义、最新取消和旧事件不能覆盖新指令的保护。

证据：`standards/test_review_standards.py`、`repro-utf8.log`、`compare_baseline.py`、`baseline-comparison.log`。4 个独立预期行为断言中 3 失败、1 通过，退出码 1；失败正是上述缺陷的证据。另6项权限、撤权、未知不重发、版本与幂等相关既有回归通过，退出码0。

Standards 合计2项发现：最高为 S1 P1；S2 属于同时观察到的功能回归，不虚构为一条不存在的编码规范。

## 5 Spec 需求符合性审查

以下按独立 Spec 审查的顺序列出三项缺失／部分实现及一项通道边界，不与 Standards 发现混排。最终复核纠正了初稿将“直接接管客户微信”视为既定需求的过强归因；用户本轮只明确提到微信发送的内容。

### R1 两个法律项目尚未挂载到四功能主流程

用户要求两个 GitHub 项目参与接待、案件整理、合同审查及庭审准备。当前 `material_codec.system_for()` 只选择群兴本地提示词，未发现家事或持衡加载路径。`docs/plans/chat-first-architecture-v2.1.md:731`、`:1058` 已要求持衡适配、回合存储、幂等及角色投影；对应 `src/cn_contract/integrations/chiheng_adapter.py` 不存在，0.6.0交接文档第48行也明确 CH-11 未完成。

本机持衡已有独立源码与此前 Windows 验证，不能说“持衡没有实现”。其本机 HEAD 与远端 `codex/windows-native-continuation` 分支同为 `8a0d640bb58c82b909409a2e689a6cecd7f06058`；默认 `main` 仍为 `e09e47fa4a93763cb50c0b8df3004bb10200cde1`。后续接入应选明确固定版本，避免误拿旧 main 代表最新续建状态。

### R2 接待知识库没有自动进入统一聊天和微信

旧独立接待页已具备私有知识目录、检索、手选片段及草稿能力，见 `web/local_server.py:203`、`web/reception_assistant.py:21`、`reception/assistant.py:17` 和 `:57`。这部分不应抹掉或重做。

统一聊天及微信主链 `assistant/material_preparation.py:51` 至 `:79` 装配当前问题、选定附件、同任务历史，没有自动读取原九份 DOCX，也没有加载 WorkBuddy 技能。因此应称“接待提示词已融合，知识自动复用尚未接线”。

### R3 无人值守是收到一批处理一批，不是自主连续办案

已授权自动策略后，后台 `service_runtime.py:489` 至 `:493` 会自动生成每批120秒许可并提交任务，**并非要求律师每批再点击授权**。一次批次提交一次主模型任务，后续补件形成新批次继续处理。

下一功能目前只是建议，`material_codec.py:30` 至 `:31` 明确不声称自动执行。代码没有把“接待建议案件整理”接成自动规划并循环执行案件整理、合同审查、庭审准备的状态机；异常时暂停，应用退出或重启后也不能凭已有记录认定具有无人值守自动恢复调度。

该边界符合现有分批设计。如果“持续推进”指本人持续补件后自动处理，现已有基础；如果指无需新指令自主推进到下一功能，该机制尚未实现。后续应明确允许自动执行的操作、累计费用和步数、停止条件、断点恢复及必须人工决定的事项，而非简单循环调用模型。

### R4 微信通道的已核实边界

`weixin_transport.py:299` 至 `:308` 仅接受扫码确认的固定本人 peer，拒绝其他发送者和群消息。目前适用于律师本人将文字和附件发给工作台；不能描述为自动接收所有客户聊天、读取微信历史或代管客户群。

回复调用 `runtime_records.py:27` 至 `:30`，回传内部工作草稿（超长截断并提示桌面查看）。当前固定本人通道下，本轮没有证据证明客户隐私外泄；若以后扩展给客户，必须先实现客户可见内容与内部策略的可靠分离。现在模型输出只是 `text + citations`，客户段落主要靠提示词约束，模型成果导出也只允许 `internal`，见 `assistant/outputs.py:128` 和 `:155`。

Spec 合计3项缺失／部分实现及1项通道边界；R1两仓未接是明确未完成事项。R4不直接计作已确认需求缺陷，客户或群消息接管属于未来可能扩展。18文件增量未独立发现必须报告的范围外功能；不存在“全部需求通过”的结论。
