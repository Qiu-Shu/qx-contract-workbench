# 恢复副本的数据库身份与停机状态

2026-11-13，接续 `6fdfb163326fbf321dbbce86400e1d571247f57c`，完成[本轮计划](2026-11-13-memory-database-binding-plan.md)的 pg0 登记与生命周期前置修复。源码现在区分同一数据身份在不同目录中的实例，并防止错误登记导致误停或虚报停机。未构建安装包、更新安装版或启用真实恢复副本。

## 行为变化

固定 pg0 0.15.2 使用系统用户目录的 `.pg0` 存放程序缓存和实例登记，不识别此前传入的 `PG0_HOME`。本轮移除该无效参数，保留已有固定依赖；实例名改为原身份加规范化运行目录摘要。运行时先取得真实目录，Windows 大小写差异不产生新名称，同身份的另一路径副本则获得不同名称。原 `instance.json` 和数据库口令不变。

启动和停止使用同一目录核对。登记指向其他目录或无法读取时不把异常当成“没有登记”，也不按旧身份名称盲目停止。没有目标 PID 文件时停止可直接完成；有 PID 文件时必须核对登记，并在 pg0 返回后再次确认 PID 文件已消失，因为上游 Python `stop()` 本身不检查命令失败。

停止未确认时，运行时保留 `error` 状态和 owner 管理记录，关闭本轮 HTTP 接口，向调用者返回错误；修复自有登记后可再次调用 `stop()`。安装宿主和开发宿主均接收该错误、记录不含秘密的消息并以非零状态退出。不能据宿主退出推断数据库已经停止；现有备份入口仍检查 PG 残留。

旧全局登记没有被扫描、搬迁或删除；新名称在正常启动时由 pg0 登记到全局目录。本轮没有把全局登记改为私有目录，也未实现自动清理旧登记。

## 实际验证

通过公开运行时及备份/恢复入口验证。真实固定 pg0、PostgreSQL 18.1、pgvector 0.8.5 与 restic 参与测试；只使用独立虚构数据库及本轮随机名称。源库经加密备份恢复后，恢复副本的标记仍在，普通运行入口仍拒绝启动。另复制其数据库和身份到明确的合成启用夹具，用于验证后续启动条件，不修改产品的启用保护。

- 原库和合成副本同时运行，使用不同登记；均回读 40 条记录、2 个合成分组、中文文本及同一备份的集群身份。
- 副本停止、重启、登记指向原库或登记 JSON 损坏时，原库仍能回读；修复登记后副本可重启。
- 健康检查口令错误但所属 PG 仍存活时，停止仍能完成。
- 运行中登记损坏时，停止返回失败、保留 owner、接口关闭；修复后重试完成停机，PID 消失。
- 原有 PG 冷备、向量索引、恢复审核及配置保留回归继续验证。

用于这组生命周期测试的 HTTP 应用是显式标注的替身，查询真实数据库的合成表；**不是 Hindsight bank API、实际业务迁移或模型语义验收**。已检查的两个开发 Python 环境没有 `hindsight_api` 和 `asyncpg`，本轮没有新增下载或安装完整 Hindsight 环境。

保留的有效失败证据包括：旧逻辑在拒绝错误登记后仍执行停止；同身份不同目录名称冲突；新增停止实现只看健康状态而漏停；运行中登记损坏却报告 stopped。最后一项由两轴独立复核分别复现，修复后另行复验。首次原生测试因旧合成夹具缺少 pg0 所需的 `postgres` 管理角色失败，补齐夹具后通过；该项属于夹具差异，不当作产品缺陷。
