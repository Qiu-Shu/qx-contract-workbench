## 已定位的失败与机制

### P2：争议阶段的自由文本试用工资绕过金额保护，错误进入三个交付面

原件明确：“以上分属不同员工，工资周期未确认。”模型在第3轮成功保存的第3项action写：

> 候选条款（乙，试用工资）：试用期月工资为3500元，试用期起止日期、工资构成与支付周期待补填；如该数额与届时适用的试用期工资法定下限不一致，双方另行书面确认调整，不溯及调整已发月份。

这里一面保留周期待核，一面把3500元固定为月工资；最后一句还可能排除已发生期间的法定差额，不能作为未知状态下的安全候选条款。应保留原数及未确认周期，删除“不溯及调整已发月份”，既往期间另按实际事实与法定标准核对。《劳动合同法》第20、26、30条涉及试用工资、不得排除法定责任和足额报酬义务，不能用这句候选概括免除。[官方文本](https://www.samr.gov.cn/zw/zfxxgk/fdzdgknr/bgt/art/2023/art_0abfdd261c03417b949df19d869add8d.html)

实际保存stage为`dispute`，六项均未传rule，返回`rule_reviews=[]`、`review_changes=[]`。`employment_review.py` 第42—50行只对明确rule或hiring阶段的试用工资topic进入程序核算；`draft_review.py` 的现有修订覆盖有限否定事实、重复试用及竞业比较，不检查工资周期新增。这是已观察到的保护范围缺口，不能说程序成功拦截了本例工资错误，也不能要求通用自然语言校验一次解决全部法律问题。最小修复应先覆盖不同阶段工资条款中的金额单位来源，以及已知未知周期不得变成固定月额。

源引用11项matched只证明引文位置匹配，不证明action中的新增单位和权利限制来自原文。

### P2：工资规则把无关缺件、合法编号和肯定月度说明都当成阻断条件

`wage-supported` 原件同时明确同一员工、同一期间、C-1以及“四项均为税前月工资标准”。模型正确提交6000/5000/2200/3500四项带标签引用，但第3、4、5、9轮保存均返回comparison=null，原因是未关联到同一可核算记录。

实际代码与只读纯函数探针定位出三项独立阻断：

1. `employment_rule_review.py` 第39行把全片段送入`parameter_context_warnings`；无关的“员工手册本次未提供”中的“未”也阻止工资比较。
2. 同函数第30—38行仅在已识别完整身份组内豁免编号；本例没有劳动者编号，linked_groups=0，合同编号C-1触发`employment_parameter_extraction.py` 第62行的带符号数字检测。
3. `_plain_gap`（第38—42行）不接受“上述四项均为税前月工资标准”这一肯定尾句；第109—110行继续将其列为未解析主体、条件或数值。

五个纯函数输入均只在内存中构造，原文件未改：

| 变体 | 全文警告 | 工资尾句警告 | `_same_wage_record` |
| --- | --- | --- | --- |
| 原文 | 未提供；C-1被识别为符号数 | 有 | false |
| 只去无关员工手册句 | C-1被识别为符号数 | 有 | false |
| 只将编号C-1改为C1 | 未提供 | 有 | false |
| 去手册句并改编号 | 无 | 有 | false |
| 再去肯定月度尾句 | 无 | 无 | true |

这证明当前解析越界，而不是模型没有看到工资原数。修复应限定条件的作用对象、识别独立编号和明确月度说明；不能直接丢弃前后句或删除所有否定保护，否则会破坏已验证的年薪、跨人、跨期防护。

### P2：相同业务阻断导致重复尝试，吞掉已授权的回读和导出

该例第2轮因source缺失被拒；补字段后保存成功但工资规则待核；随后3次更换引用/保存、3次调用提取接口，其中一次把引文end写为101而实际含句号需102，被程序正确拒绝。10轮最终没有模型回读与导出。完整调用顺序是get_case、read_case_material、save×4、assess×3、save×1。

不能仅增加轮数后宣称修复。应让重复的同类业务阻断返回具体可处理原因；源未变且再次相同阻断时，保留待核项并完成其余意见的同note回读/导出。当前Skill第38、48行已有“继续其他意见”的要求，实际行为未遵守。

## retest3事实提取诊断：支持与不支持的根因判断

六条均完整读取；prompt/expected匹配`diagnostic-cases.json`，4项冻结文件摘要一致。模型均deepseek-flash，systemSha256与skillSha256与retest2一致。改动因素是“只做事实JSON提取”的任务指令，不能把结果当原完整审查任务的通过，也不是随机对照因果实验。

| 诊断原答 | 观察 | 剩余限制 |
| --- | --- | --- |
| [G-1](model/retest3/diagnostic-G-1.json) | 四项均记元/年，支付频率另记，4800元/月是提议而非原约定或已核标准。 | 仍写“用户口头给出”；将提议状态填为“未协商、未签署、未生效”，未保留这些客观状态未知。事实阶段本身仍会新增信息。 |
| [G-2](model/retest3/diagnostic-G-2.json) | 同样正确保留四项年单位与4800提议。 | 将拟修改字段确定为“合同工资”，原问题未明确指4800替换四项中的哪一项；不能把歧义直接填实。 |
| [H-1](model/retest3/diagnostic-H-1.json) | 明确未读考勤，无法确认具体日期、打卡时点、缺勤天数或性质；公司和员工陈述分开，其他程序未知。 | 只证明本次提取未重复具体考勤内容错误，不证明后续通知能继续保持。 |

**证据支持的有限解释：** G的年单位、H的考勤未知在纯提取任务两次均保留，而完整审查在最终条款/通知发生偏移；因此不能把此前错误简单归为模型从未读懂输入，后续拟稿中未持续约束字段是可检验的机制。与此同时G-1、C-2仍补造口头来源，G-2仍填实歧义，说明事实提取也不可靠。

**证据不支持：** 不能据此认定唯一根因是上下文长度、模型能力不足或提示词长度；不能断言拆成两步即可解决；不能把引用matched、同note导出、功能完成或本次诊断观察当完整法律审查质量保证。当前最明确的工程缺口是条件作用范围误判与跨阶段工资自由文本保护遗漏；模型侧还存在输出阶段的事实漂移和重复尝试。上述问题仍未修复，维持候选、不据本批开放。
