# 第一性原理设计3：让常见调用只提交材料与任务

2026-11-16。只读设计，基线 `8fd8ce4ff55582cbe218950bced231b243ce17ff`。本稿未调用模型、未改产品、未改变候选状态。与其他设计并行，提出方案不等于已实现。

## 已确认的问题与尚未确认的因果

目标是从材料生成有用、可核对的意见及候选正文。最基本的不变量是：交付正文中的事实不得比材料及明确推导多出一个未经支持的断言；未知不能变成否定，单方转述不能变成另一方直接陈述，计价周期不能凭习惯补齐。法律条件和拟议条款另有身份，不能反向成为案件事实。

现存证据已经证明**来源定位成功不等于输出命题获支持**。`first-principles-probe.json` 的 D/H/J 均有匹配引文，错误候选仍留在文书。`litigation_documents.py:133` 将是否有匹配引文作为段落来源状态；它没有证明任意 `text` 被引文蕴含。声明“待核”不能撤销同段已经写出的确定事实。

`retest4` 则证明了两个不同失败面：A/D/H/J是正文内容错误；F 的8192个输出token全部是推理、正文为空，是未完成。不能把F计为法律错误，也不能把加大输出额度后的完成率当成其他错误已经解决。B/C/E的媒介标签错误应单独记账，不能与金额或正文事实错误合并成同一种严重度。

尚无对照实验证明“提示词太长”“模型能力不足”或“分阶段一定更好”。这些目前都是可检验假设。把同模型换成短提示后偶然答对，不能单独证明原因就是上下文长度。

## 常见 caller 的最小 interface

外部 seam 放在“当前对话已有材料，准备交付一份审查/候选文稿”处。caller 不负责选工资规则、拼引用、挑导出器或重试待核状态。

```python
result = prepare_employment_delivery(
    case_id=current_case,
    request=current_request,       # 原请求，不要求用户再填事实表
    request_id=current_request_id, # 同参数重试，不重复保存
)
```

返回值的关键字段：`status`、`note_id`、`body_text`、`files`、`pending`、`coverage`、`source_snapshot_id`。`status` 只表达流程状态：`delivered`、`delivered_with_pending`、`source_changed`、`incomplete`。内容身份另列：来源陈述、条件分析、拟议文字，不设置一个“模型确认事实真实”的布尔值。

常见情况一次请求得到同一保存版本的正文与文件；缺失信息只影响相应条款，已有信息不重复问。确实缺少执行所必需的案件或文件时，返回具体缺口；不能以“待核”为由反复调用模型或重存相同记录。材料版本改变时不能悄悄沿用旧结论，返回需要重新读取的来源范围。

这个 module 的 depth 来自把版本核验、来源保持、阶段推进、失败归因和同稿交付藏在一个 interface 后面。若删除它，这些顺序约束会重新散到每个 Skill、工具 caller 和评测脚本里。

## seam 后的四个阶段

| 阶段 | 模型可以做什么 | 程序必须保持什么 | 可观察的失败 |
| --- | --- | --- | --- |
| 来源记录 | 在实际读取材料中选择相关片段、提出议题分类 | 当前案件/版本/片段/原句完整回读；引用窗口含限定语；原文与未知信息原样保留 | 漏选、错选、跨人跨期、限定语截断、过期引用 |
| 议题与规则 | 按请求选择议题、关联支持和相反材料、提出条件性路径 | 来源记录不可被后续改写；金额只经现有精确计算；规则身份与法源独立 | 规则选择错误、遗漏反证、无条件适用、未完成 |
| 候选正文 | 提出措辞、请求核实项、规范性约定和条件分析 | 每个事实块只引用来源记录；无依据断言不能被当作事实块；不删掉可支持的候选内容 | 意见正确但条款变义、把未知写成否定、主体替换、法定范围收窄 |
| 保存与交付 | 无需再写一份独立事实/意见 | 保存、Word、聊天取同一正文；出错保留审计但不把旧草案冒充最终稿 | 重复保存、导出旧稿、正文与文件不一致、假文件链接 |

来源记录首先是一份“材料说了什么”的记录，不是自动事实认定表。模型自填的 `speaker=公司`、`state=已发生` 仍然可能错；不能因为它们进入JSON就变成可靠事实。默认由程序以“所引材料记载：〔完整原句〕”显示，只有原文及可验证结构明确支持时才生成更具体归属。事实未确定时，候选通知仍可以直接询问日期、出勤或通知情况，不必先虚构一个“查明”前提。

自由文字必须有明确身份：`source_statement` 引用材料记录，`calculation` 引用已核算结果，`conditional_analysis` 指明前提，`proposed_term` 描述未来约定，`verification_request` 提出问题。这个分类有助于约束，但**模型自选分类不是语义安全证明**。例如把“此前从未试用”塞进拟议条款仍是历史事实断言，不能因为块类型为 `proposed_term` 而放行。

第一版只把有可验证构造方式的事实表达、计算和高风险法律范围交给程序；其余自由分析保留明确的审查状态。不要承诺建立通用蕴含引擎，更不要把所有未知情况变成空模板。

## 可直接复用的 implementation

- `bridge/source_bound_litigation.py:40` 的 `_reference` 已核验案件归属、当前摘要、片段及唯一原句位置；`:111` 恢复句界，但注释明确它不是语义认证。
- `bridge/source_bound_litigation.py:203` 的 `build_source_bound_litigation` 已拒绝任意模型事实正文；接收引用、计算、有限诉求/争点，保留反对材料与缺口。它是来源记录与受约束文书的可用底座，**不是完整劳动合同修改器**，不能改文件名就冒充完成全部需求。
- `business_server.py:340`、`:365` 的条款/解除初审工具已有自然语言参数提取、条件清单及记录/导出流程；优先用现有能力，不强迫用户把材料重写成程序特定格式。
- `generate_litigation_document` 的 DOCX 排版、内部来源稿、真实交付回执可以复用；其 `text+citations` 语义弱点不应原封不动成为新 module 的事实输入接口。
- `save_employment_review` 的业务待核状态、来源记录、精确工资规则及同稿交付有用；原有有界正则可以作为补充诊断，不能被描述为任意正文的保证。

依赖策略：纯计算与规则选择属于进程内；案件SQLite、材料仓库及DOCX发布属于本地可替换依赖，沿用合成案件测试；DeepSeek为真正外部依赖，注入模型调用adapter，生产与记录回放两种adapter都有实际用途。只在内部保留抽取/写作等 seams，不把阶段API暴露给用户增加点击。

## 对照实验：每个比较只回答一个问题

固定模型、thinking high、事实输入、参考日、法源版本和单案例总输出上限；沿用 `employment-live-20261116` 台账，不重置剩余额度。保留请求、输入哈希、自动中间结果、原始回答、结束原因、实际正文。预先冻结判分项，所有失败都保留，不挑“最好的一次”。建议先预留不超过1.5元实验额度，实际运行仍以总10元硬上限核验为准；本稿没有发起消费。

| 对照 | 唯一主动改变的变量 | 能支持什么结论 | 不能声称什么 |
| --- | --- | --- | --- |
| 原始完整说明 vs 保持任务/相关约束原样、移除不相关流程说明 | 与本任务无关的说明是否存在 | 不相关指令负担是否影响此组任务 | 不能直接归因于纯token长度；删除文字与减少长度同时发生 |
| 同一写作提示、原材料 vs 原材料加自动产生且冻结的来源记录 | 是否提供结构化来源记录 | 来源记录能否降低“分析知道、正文遗忘”的迁移错误 | 不能用手填正确事实替代自动记录，也不能删掉原材料后说信息相同 |
| 同一个自动来源记录、同一任务预算：一次综合生成 vs 分配给议题/候选两个阶段 | 任务是否分阶段，累计输出额度保持相同 | 分工是否在同成本约束下提高可用交付 | 不能说多次调用天然更强；若总额度增大则是混杂变量 |
| 同一原答经当前交付链 vs 新的受约束交付链离线重放 | 交付链 | 引文通过但错误正文存留是否被接口本身阻断；是否误删有效候选 | 这是确定性工程验证，不是模型能力提升 |
| 来源记录已独立核对正确的失败样本，仅要求一个原子任务 | 任务范围 | 在此输入与预算下，特定能力仍失败还是只在组合任务失败 | 少量失败不能证明模型绝对能力上限 |

“自动来源记录”必须由实际模型/现有提取程序从同一材料产生，未经人工改好。独立审阅只标注正确或错误，不修改后送入写作。错误记录保留并计入端到端失败；正确记录子集可以用于定位写作阶段，但必须报告被排除的记录和数量。人工标准答案可以作为评分依据，不能作为生产输入后计作自动通过。

为了区分提示语义与纯长度，可选增加一个长度对照：在相同任务提示前放等长、明确无关的中性内容，其他文字不变。若不能安排这个对照，只报告“指令打包方式影响”，不写“上下文太长已被证明”。

F 的预算问题单独处理：先确认 `finish_reason` 与正文状态；如比较不同输出上限，则明确这是预算单变量实验，不能与同预算分阶段实验混在一起。所有条件中推理token都计入上限，不只统计可见正文。

## 不靠三道题硬编码的验收

D/H/J用于复现，另冻结未参与修复的合成变体；这些变体改主体、期间、材料顺序、肯定/否定/未知、陈述链和合同编号，但不得改写法律规则来迎合程序。至少包含：换岗而非换关系的试用；“邮件转述口头同意”与“公司直接确认”两种来源链；已明确拒绝/明确同意/未说明三种状态；计价年、支付月；两人金额相邻；完整已知正例。只在D/H/J写替换字符串不能通过这些变体。

成功标准分开报告：

1. 原文内容、陈述主体、金额及单位、否定和未知状态在可交付正文中无新增断言；关键反例0项漏出。
2. 材料明确支持的实质意见和候选仍交付；不能靠全部变成“待核”取得安全通过。既有工资正例必须输出有前提的具体候选，未知考勤例必须输出可使用的中性核实文字。
3. 来源记录阶段的错误率与正文阶段的错误率分开；功能链完成、实际正文质量、流程未完成也分开。
4. 实际MCP读取、保存、回读、Word与最终聊天的语义内容一致，材料不变，输出链接可用；这组是生产路径验收，无工具全文只是模型诊断。
5. 有意跨案、过期版本、引用截断和被注入指令不能变成事实来源；失败不丢失其他已支持的独立事项。

实施建议：先做上述离线交付对照和自动来源记录的小实验，再决定是否把完整四阶段编排做进产品。推荐深化已有来源绑定实现，并让最常见caller只有一个入口；不建议继续通过越来越长的提示词或越来越多字面替换承诺通用可靠性。若小实验没有改善，就据其失败阶段调整设计，保留候选身份，不能用“架构更规范”替代质量证据。
