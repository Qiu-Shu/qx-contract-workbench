# 0.2.16 审核首批整改

用户于 2026-11-11 要求落地已讨论的五项可靠性整改。基线 b802e214（相对 v0.2.16 仅发布文档变化）。现行产品是 harness；原工作目录及其他任务改动不动。使用现有实现、合成数据和本机运行时，不接新组件、不调用真实模型、不登录微信、不发布或覆盖用户安装。

## 实施与验收

1. R01/R02：knowledge-store/runtime/api/client。先将新机导入、刷新、重启、再导出再恢复、明确删除不复活、旧项目备份合并、历史/重复/多页/回滚场景写为失败测试。持久区分从备份迁入但本机未核对的来源与已删除来源；所有缺失来源路径一致处理。恢复按目标库当前会话绑定归属，记录归属冲突，历史亦归于当前条目，保留人工更正。界面说明来源暂不可追溯。再跑知识相关回归。
2. R03：wechat/state.js 及已有加密模块。先验证合成 token 明文问题；复用 Windows DPAPI，覆盖账户及 context token，首次写入只写密文。旧明文迁移必须先加密、回读校验，失败保留原件并报错；不静默降级。验证重启、迁移中断、损坏及失败路径，仅使用虚构凭据。
3. R04/R05：sources/media-source-registry.json、packaging/stage.cjs、相关 Python 打包测试、测试运行入口。核对受控基线已有注册表，入库并纳入显式覆盖，验证干净 payload 服务首启。修过时测试，分可移植离线、Windows 集成、真实模型评测入口；真实模型不默认运行。明确前置依赖，不能通过跳过产品缺陷制造全绿。
4. 集成：目标回归、可持续测试入口实际执行、独立审阅，记录命令/退出码/数量与未验证范围。完成后本地提交；不默认推送、发布或安装。

## 分工与边界

主代理负责 R01/R02 及两份旧知识 API/runtime 测试。独立代理负责 R03；另一独立代理负责 R04/R05（不修改知识测试）。共用隔离源码目录，文件所有权分离，不操作用户业务库。并行代理依据 dispatching-parallel-agents 技能处理独立故障域，最终另作独立审阅。

## 验证重点

- 导入的缺失来源不能擦除正文/引用/历史；有删除标记不能被旧备份复活。
- 当前绑定优先，旧项目的列表、检索、上下文及原文追溯不能泄漏新项目摘要。
- 不改变已有条目的人工作业结果，不因多页顺序/重复导入覆盖已有修订。
- 凭据加密失败不得写明文，迁移失败不得丢掉唯一凭据。
- 干净运行配置和测试模式显式选择；Linux 或模拟验证不冒称 Windows/真实微信验收。
