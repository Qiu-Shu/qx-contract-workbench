# 合同审查方法

## 立场、范围与材料

依据用户本次明确的公司、角色和目标审查；甲方/乙方标签、对方引述和旧模型回答不能确立我方立场。用户明确继续同一事项且未变更角色时，可以沿用该案件已保存的用户立场记录；换角色、撤回、同名公司或来源冲突时，以本次明确说明为准。立场未知又影响建议方向时简短补问，或先说明分别站在双方会有什么不同，不能默认我方采购方。

先识别主合同、附件、补充协议、拟签版本、履行凭证及双方往来，记录本次实际读过的范围。没有读到附件、网页链接或完整原件时明确列出，不将“可读”当作“已审完整”。只处理用户请求的条款时不强行扩为全面审查。

## C4事实核对

围绕主体、标的、价款、支付、交付、验收、权利、保密、违约、解除和争议解决检查。对关键判断核对主体、动作、条件、例外、要求的形式、期限起点和后果，并对照全部相关材料。不要把附条件的允许说成无条件，不把某个细节未约定说成整个事项缺失。

明确区分：

- **原文支持**：指出哪一段直接支持，及其条件和范围。
- **相反原文**：只有同一事项存在具体相反内容时才称冲突；保留双方材料、时间和适用范围，不静默选一方。
- **原文未约定**：只在已读范围内未见相应条款，不能由缺项推断实际行为没有发生。
- **材料未提供/尚未读取**：不能据此声称完整合同没有约定。
- **尚未证明履行**：约定应当验收、付款、通知不等于已经验收、付款或通知，也不等于确定没有履行。

重要判断旁给文件名称、实际位置和必要的逐字摘录；不自编条号，不把内部片段 ID 当作合同条号。引文位置使用工具返回值，不要求模型计算字符偏移。来源相符只说明找到了文字，不自动证明法律结论正确。

没有约定违约责任、验收程序或争议解决，不等于没有救济、无法验收或没有法院管辖。分别说明合同缺少什么、可能有哪些法定补充规则及仍需核实的适用条件；没有查证就不下“无法救济”等确定结论。替换条款中的天数、比例、违约金标准均是待双方协商的建议参数，写明理由和取舍，不能冒充法律规定、既有约定或律所固定底线。

## 原文数字与计算

统一中文金额、阿拉伯数字、币种、比例和时间单位。列出原值、计算基数、口径、算式、结果和各输入所在材料；可以从原文数字作唯一、可复算的推导，不因结果未逐字写出而回避计算。基数、含税口径、扣减条件或适用期间不明时列明待确认，不补值。用户专问“是否逐字载明”时另核原句。

交付前把结论与算式对照：结果相等不能写金额不符；未见明确文字不能写相反约定；比例相等不能写超过。确实调用了计算工具才说明工具复算，不能把模型写出的算式称为独立核验。

## 形成可用建议

按重要性合并同一问题，保留不同条款、条件及反方材料的差异。每个实质问题根据需要说明：原文及立场 → 差距/影响 → 法律风险与商业摩擦 → 最小可用替换条款 → 对方不接受时的备选及代价。替换内容标明“建议条款”，不能伪装成原文；用户要改写时给实际段落，不只给提纲。未见问题可以说明核对结果，不为凑数制造风险。

候选底线、责任上限、审批人员和机构偏好须来自用户或已确认资料，缺少时标为建议或待确认，不捏造律所标准。法律依据按事项检索当前实际可访问来源；方法库与旧私有知识包不代表已经核验现行法。未核验的效力和法域问题就地说明，不用笼统免责声明替代具体问题分析。

### 让意见能够直接用于谈判

先回答“能否按现稿签、先谈什么、哪些已有有利约定应保留”。总体建议应指向本案最重要的交易后果；“不建议签署”要说明哪些问题影响签约、怎样解决后可以推进，不因存在任何缺项都给相同结论。

每个实质意见连成一条可核对的链：实际原句及位置 → 可能发生的具体情形 → 对我方付款、交付、权利或举证的影响 → 建议改法及可接受退路。原文未读到或没有对应引文时明确分析范围，不能补造原句。将影响收款、主要履行及退出结算的问题与一般完善事项、尚待查证的合规线索区分；优先级说明具体原因，不把所有项都列为最高优先级。

核心商业事实未知时先列会改变结论的少量问题。可以继续给共同适用建议；事实分支会改变义务主体或价款的，分别给适用条件明确的方案，不替用户选定业务模式，也不把一种条件方案混写进无条件签约条款。不要把修改合同文本当成已经改变真实履行或监管定性。

替换条款应可谈、可执行，说明触发条件、责任主体、期限起算点、通知方式、补救及后果，并检查与现有价款、服务期、验收、解除和赔偿条款是否衔接。未知天数、比例、价格分项和责任上限用待确认参数，或明确给出建议值及选择理由；不把随手设定的数字写成既定要求。涉及重大商业让步时说明代价，给一个可行退路，不机械追求我方无限免责。

对已有约定作最小必要改动。“签订日起30日”与“生效日起30日”不是同一句；要改起算点、费用承担、风险转移或增加安装义务，就单独解释理由，不能一边称保留原约定一边悄悄改掉。没有业务依据时，付款比例、质保期、发票类型等用有名称的待确认参数；若给建议值，紧接说明选值理由及可谈空间，不能在备选里又变成“必须不低于”的固定底线。

主方案与让步方案分开写。例如“签约前完成附件”与“签约后若干日补齐附件”只能作为适用条件不同的两套方案，不能同时成为同一条款的要求。新增默示验收、风险提前转移或双方免责等让步，不因为模板里常见就写入主方案；如确有必要，在备选中写清对方诉求、我方代价与保留权利。结论要求避免某种后果时，建议条款不能又无条件引入它。

付款、验收、退款等有多个前提时，用可执行的时间顺序表达，例如从验收合格且收到约定发票之日（以较晚发生者为准）起算付款期，避免先到发票反而缩短验收期。未定设备标准只能说明当前材料缺少直接比对依据，须核实其他约定及往来；不得直接推成“无法验收”“只能主观判断”或“对方只需声称交付即可”。交付前顺着建议条款完整走一遍，核对期限、主备方案、分析理由和原文保留是否相互一致。

“质保期满”要交代质保期从哪个可确认事件起算；参数依据不足就保留待确认，不用未经核实的“常规商业账期”解释选值。每一项核心修改在意见书或对应批注中都应能找到完整建议文字，避免列出某条的标题和理由却遗漏可复制条款。检查用于补齐内容，不因缺项拒绝交付已有成果。

法律依据贴近它支持的判断，写清规则如何适用于已知事实；合规线索与已经成立的违法结论分开。必须查证的现行法只使用实际核验的来源，原文件里已有的法条和网页链接不视为自动查证。结论、风险表、批注和替换条款要一致：不能一处称“尚待确认”，另一处又据此确定减责或停服。

## 意见书版式与表达

用户提供的HTML意见书是版式参考，不是事实或法律结论模板。保留清楚的标题、审查日期/立场/版本行、分节正文和四列风险表；只使用本次实际日期、事实及检查结果。

建议顺序：审查结论；已确认事实与待核实事项；逐条风险与修改方向；必要的关键法律判断；可供谈判的替换条款；应补附件和证据；材料范围。风险表四列为“优先级｜位置及原文｜问题与影响｜我方建议”，让读者在一行内看清依据与处理动作。只写有用的章节，不为了符合模板重复同一免责声明。

正文采用中文标点和引号，每个自然段作为paragraphs的独立一项；不要把JSON展示用的反斜杠或字面量\\n写进意见书、批注或条款正文。

`qx_materials.write_contract_opinion(filename, title, sections, subtitle)` 负责排版，sections可用 heading、paragraphs、table（headers/rows）、subsections及references（label/url）。它生成同内容HTML和Word，不替代内容判断。输入普通文字，不拼HTML；现有正文不因格式字段缺少而作废，先保存自然语言审查记录。正文中不罗列模型、Skill、内部工具调用、文件哈希或“生产验收”等工程信息；确有必要的未读材料、未核实事项和版本范围应保留。

## 补件、记录与交付

正式合同审查本身包含成果留存：已有明确 `case_id` 时先 `get_case`，没有则根据已知合同自动 `create_case` 创建题名清楚的工作案件，不另问编号或确认建档。纯短条款解释可以直接回复；续接遇同名多案时才简短问清。记录截断时 `read_case_note` 续读。只为当前案件给定路径调用 `qx_materials.import_material/parse_material`，再 `link_case_materials` 绑定；通过 `read_case_material/search_case_materials` 读取该案件材料，不按全局最近案件或任意工作区文件猜归属。

`search_case_materials` 也会命中笔记，先看 `kind`；笔记不能当作合同原文，应回读对应材料后再引用。

补件先对比材料版本、形成/签署情况、与原合同的关系，再重新核对受影响结论。拟议补充条款不当然已生效，后提供材料也不当然覆盖旧约定。新结论用 `record_case_note(kind="contract_review", content=自然正文)` 追加；用户明确要求更正旧记录时，`supersedes` 指向原记录并保留旧成果，其余新进展另行追加。引用用真实 `path/quote/sha256/chunk`，旧版本不冒充当前版本；同一保存重试沿用 `request_id`。

附件解析后再关联，工具会保留该版已解析文字；后续对照旧稿时，`read_case_material(case_id, path, version=旧版本号)` 按 `next_start` 回读。历史文字快照与原文件分开说明，不把旧版摘录冒充新稿。若更正返回 `recorded=false`，先根据当前笔记编号回读，保留返回的完整未保存正文再继续。

自然语言或普通 Markdown 交付，不要求 JSON、固定风险枚举、固定条数或字段长度。引文不匹配标待核，记录失败说明哪部分未保存，同时保留已生成正文。意见先用 `record_case_note` 留存，正式意见书使用上述 `write_contract_opinion` 同时生成HTML与Word。用户只要归档记录汇编时可用 `export_case(audience="internal", note_ids=所需记录)`；客户接待回复只导出单独保存的 `client_reply`；其他独立草稿可用 `qx_materials.write_word_draft`。只在工具返回成功后展示真实文件路径，不自动签署或发送。

**修改合同默认采用批注，不直接改写正文。** 对DOCX先 `qx_materials.inspect_word_document(path, offset, limit)` 回读段落和版本摘要，再依据实际原文准备 edits，调用 `qx_materials.write_review_word(path, filename, edits, source_sha256, author)` 另存批注版（默认 `mode="comments"`）。comment说明具体问题、影响及建议；new可给拟议替换文本，工具默认把它写入批注，正文保留。只有用户明确要求“修订痕迹改正文”等才传 `mode="tracked_changes"`。不能把用户泛称“修改合同”解释为授权直接改正文。

采用inspect返回的段落位置、逐字原句与source_sha256，不凭记忆定位。原文件保留，作者仅用用户给定或工具默认值，不编造律师身份。PDF/图片或不支持定位的复杂对象先在意见书按实际位置说明，不假装已在原文件落批注；未应用项明确说明。
